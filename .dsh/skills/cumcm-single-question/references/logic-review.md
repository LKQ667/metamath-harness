# 本问逻辑对抗复核

本细则将来源评审的六类检查、证据要求、人读与机器读裁定、致命错误门禁融入单问流程。只在主技能第 4.5 步内执行；此文件是本地参考正文，不是另一个技能入口。不得调用外部 comp-review、comp-modeling、comp-code、comp-paper，不安装或下载这些技能，不调度新的技能链。

## 执行范围与证据输入

默认随本问求解执行。来源中的 `_resolve_template`、`enable_comp_review`、`MH_FAST_MODE`、`CLAUDE.md` 快速跳过及专用 `_utils` 脚本属于原宿主机制，不移植、不探测、不执行。用户明确要求跳过复核时尊重要求，记录 `skipped` 与理由，不能写成通过；不能假定其他阶段已代做检查。初探仅静态核对现有证据，记录 `static_only`，不运行模型、不强制落盘、不声称数值通过。

先读摘要和有关段落，再定向读必要字段、代码及数值；禁止整包倾倒大型结果 JSON。不存在的材料不伪造，不要求为兼容来源补建整套工程：

| 来源中的材料 | 本问采用的等价证据 |
|---|---|
| PROBLEM_ANALYSIS.md | 题目原文、第 1 步验收目标、概念对齐及硬约束 |
| DATA_FACTS.json | 数据字典、预处理审计、关键观测变量及观测范围 |
| MODELING_REPORT.md / LOGIC_CONTRACT_MACHINE.bounds | model.md 中假设、上下界、目标/约束的原文依据及代码实现 |
| CROSS_PROBLEM_LEDGER | 本问必要前置依赖、上游结果的单位、范围、不确定性与运行来源 |
| RESULTS.md / AUDIT_REPORT.md | result.md、runs/ 中已有验证和审计记录 |
| figures/*_results.json | 项目唯一结果源或 results/final_results.json 的必要字段 |

先复用已有确定性检查（若存在 logic_audit / cross_problem_check，也只读取其有效记录），核对输入、代码与运行版本是否仍适用。未实际执行或已过期的检查标为未验证；没有专用工具时采用本地核算与反例，不虚称已兜底。复核聚焦已有检查未覆盖的语义错误，修改后只重验受影响项。

## 六类逐项核对

先暂置已有推荐与建模解释，从原文和观测事实重建判断，再对照实现。每类给出具体原句、文件行号、字段路径、运行引用或数值证据；不适用须说明理由，缺证据记未验证，不能凭直觉断言错误。

1. **任务理解 `task_alignment`**：逐条对齐原文要求与目标函数、约束、关键量及最终输出。检查是否把求 A 做成求 B（如覆盖宽度换成面积）、min/max 颠倒、约束语义相反、物理量含义错误或遗漏明确任务。任务读歪、目标搞错属于 fatal。不能仅检查实现是否忠于建模说明，必须检查说明是否忠于原文。
2. **方向与界 `bound_direction`**：将模型声明的上下界与代码比较；对删失、封顶、反解代入实际观测或有依据的边界例子验证不等号方向。检查可行域、极限情况和单位，系统性方向错误属于 fatal。
3. **重复计量 `double_count`**：对每个“总量=A+B”追溯拟合与标定来源，确认 A 是否已吸收 B，例如以含分项的总量拟合截距后又加该分项。给出公式和数值分解，造成系统性偏差的重复计量属于 fatal。
4. **外推措辞 `extrapolation`**：比较预测条件与实际观测范围（必要时检查多变量组合支持域），超出支持范围时标为情景模拟、假设外推或需现场标定，不能写成确定的数据结论。检查区间和可靠性主张是否有证据。
5. **遗漏真实变量 `missing_feature`**：追踪关键实测变量（含已有台账的 role=observed）进入模型、被聚合或被排除的原因。被称“不重要”却无机制、数据或消融依据时提出具体质疑；不强制所有变量入模，防止把泄漏、冗余或不可用变量硬塞进去。
6. **跨问一致性 `cross_problem`**：只沿本问真实依赖链对照上游峰值、边界、资源总量等与当前约束/结论，检查单位、时间尺度、情景及不确定性。相同条件下的硬矛盾属于 fatal；条件不同先解释差异。不因此自动重算全题，无跨问依赖时记不适用。

复核仍可能与求解共享认知盲区，不能承诺无遗漏。这里的独立视角指从原始证据重新推理，不等于独立模型或独立实现；不要求新增 AI 调用或子代理。

## 裁定与本问产物

`COMP_REVIEW.md` 按六类列检查覆盖、问题描述、严重性、定位、证据、修正建议、处理状态与残余限制。清楚区分“检查无发现”“不适用”“未验证”。问题编号跨轮次保持稳定，已解决问题保留原证据及修复后的运行引用。

`COMP_REVIEW_VERDICT.json` 使用以下结构（仅格式示意，不能把示例当真实通过结果）：

```json
{
  "status": "blocked",
  "review_round": 0,
  "repair_cycles_used": 0,
  "max_repair_cycles": 2,
  "input_refs": [],
  "checks": [],
  "findings": [],
  "fatal_count": 0,
  "unverified_count": 1,
  "stop_reason": "尚未完成实际复核"
}
```

- `input_refs` 记录原文、代码、数据、结果的路径与版本/指纹或 run_id，裁定只适用于这些证据。
- `checks` 每类一项：`category`、`state`（checked / not_applicable / unverified）、`evidence`、`reason`。六类均须覆盖，空数组是未完成。
- `findings` 每项含 `id`、`category`（上述六个枚举之一）、`severity`（fatal / major / minor）、`where`、`evidence`、`fix`、`state`（open / resolved）、`verification_refs`。
- `fatal_count` 从尚未解决的 fatal 实际计数，不使用声明值替代核对；`unverified_count` 从未验证检查计数。JSON 缺失、解析失败、字段缺失、计数不符、覆盖不全或版本过期均不得默认为零或通过。
- `status` 为 passed / passed_with_caveats / blocked / skipped / static_only。只有有效裁定、六类均已检查或有依据地不适用、无未验证项且无未解决 fatal 才能通过；仍有 major/minor 时为 passed_with_caveats，在 result.md 和后续采用的文字中逐项披露并限制结论。

fatal 阻止受影响路线被包装为可信最终解；major/minor 通常不硬拦，但必须披露外推、假设及待验证边界。严重性按后果判定：若遗漏变量或不受支持的外推已使核心答案失效，同样升级 fatal，不因类别名称自动降级。其他有效路线可继续交付；全部受阻时交付失败证据和缺口，不输出虚假已验证排名。

## 有限修复与终止

本次请求按“首次复核（review_round=0）→必要局部修复→复核（1）→必要局部修复→复核（2）→终止”执行，最多两轮修复、三次复核；无问题立即退出，不能为了用完次数追加工作。修复沿用第 4 步的总计算预算与停止规则，任何上限先到即停止。

复核本身只提出裁定；确有可修复问题时，在当前技能内局部修改推导、实现或表述，并重跑受影响计算和验证。不得重新进入第 0 步，不重新加载本技能或外部技能，不重新发散全部候选，不重置计数、实验预算或同因失败历史。已有路线深化仍只修所选路线。

无新修复依据、同因错误重复、关键证据缺失、运行不可用或预算耗尽时立即结束修复，保存 blocked 与明确原因、未解决项、最后有效结果和下一步所需条件。任务理解错误需要全新建模而超出剩余预算时亦如此；“致命错误必须修”表示不得放行，不表示无限重试。恢复同次中断执行须读取既有轮次并续计，只有用户明确发起新的求解或修复请求才建立新批次。

第 5–6 步使用当前有效裁定，不再无条件触发全量复核；后续改动使证据失效时在剩余轮次内定向复核，已无额度则受阻交付。初探的静态检查不借此升级计算，跳过状态也不能转为通过。
